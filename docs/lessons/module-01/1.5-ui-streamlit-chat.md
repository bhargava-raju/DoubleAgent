## Concepts

### Streamlit's execution model

Streamlit turns a Python script into a web app. Its one big idea:
**the whole script re-runs from top to bottom on every interaction** (a click, a chat message).

| Streamlit | C# / Blazor Server mental model |
|-----------|---------------------------------|
| the script | a component's render method |
| a widget call returns its current value (`model = st.selectbox(...)`) | `@bind` on an input |
| `st.session_state` | component/circuit state that survives re-renders |
| `st.rerun()` | `StateHasChanged()` plus a fresh render |
| `with st.sidebar:` / `with st.chat_message("user"):` | a layout container (`RenderFragment`) |
| `AppTest` in tests | bUnit |

So: anything you need to keep between interactions (the chat history) goes in `st.session_state`.
Everything else is recomputed each run, which is fine because it's cheap.

### Keep the UI thin

`app.py` only renders and collects input. All app logic goes through `ui/backend.py`, which calls the code
you've already tested. That's why the UI tests can swap `backend.answer` for a fake, and why Module 7 can
replace Streamlit with a FastAPI front end without touching the agent.

### Async inside Streamlit

Streamlit scripts are synchronous. Bridge into your async code with `asyncio.run(backend.answer(...))`, the same
trick as in `cli.py`. (Module 4 adds streaming, where this changes.)

### Python you'll use

- **The walrus operator** `:=` assigns inside an expression:
  `if (err := backend.config_error()) is not None:` ≈ C# `if (GetError() is { } err)`.
  Also: `if question := st.chat_input("..."):` runs only when the user submitted something.
- **Module attributes as seams**: tests use `monkeypatch.setattr(backend, "answer", fake)`. That only works if
  `app.py` calls `backend.answer(...)`, not a name imported with `from backend import answer`
  (that copies the reference at import time). In C# terms: depend on the service, not a captured delegate.
- **Dicts as lightweight records** in session state: `{"role": "user", "content": "..."}`.

## Pillars in this lesson

| Pillar | Notice | Do |
|---|---|---|
| 🧭 Orchestration | The UI doesn't orchestrate; it hands one question to the agent and shows the result. | Explain in `notes/1.5.md` why the history in the UI isn't sent to the agent yet. |
| 🧠 Context & memory | `session_state.history` is *UI* memory. The agent still sees only the latest question. | Pass the previous turns to `run_agent` so follow-ups work ("and what are their payment terms?"). Keep the existing tests green. |
| 🛡️ Guardrails | The app refuses to start without config, and `max_turns` is a user-visible control. | Disable the chat input while a request is running, and cap question length at 2,000 characters. |
| 🔐 Security & privacy | The API key never reaches the browser; only the server process holds it. Anyone who can open the URL can spend your tokens. | Run with `--server.address 127.0.0.1` so it's only reachable from your machine. Add that to your notes. |
| 📏 Evaluation | `AppTest` pins UI behavior; it can't judge answer quality. | Add a 👍/👎 button under each answer (`st.feedback`) and store the result in the turn. That's your first human feedback signal (Module 6). |
| 🔭 Observability | Users see tool calls, which builds trust and helps debugging. | Show turns and elapsed time under each answer with `st.caption`. |
| ⚡ Performance & cost | Each rerun re-executes the script, so expensive work must not run on every rerun. | Cache the supplier directory with `@st.cache_resource` and explain why `cache_data` would be the wrong choice. |
| 🔁 Reliability | An API error currently crashes the page. | Catch `anthropic.APIError` and `MaxTurnsExceeded` in the chat tab and show `st.error` with a retry hint. |
